## What each class means

- **pass**: the statement did what DuckDB's file expects, or the query's answer matches.
- **refused**: Burrmill refused with an error naming what it does not support (`not in the
  admitted subset`, `not supported`, `not implemented`).
- **wrong**: Burrmill answered and the answer differs, or a statement DuckDB refuses succeeded.
- **error**: any other error, a statement timeout, or a crash.
- **skipped**: the harness could not give the record a fair run; the reasons are below.

A record is one `statement` or `query` in a file. One inside a `loop` runs once per iteration
and counts once, as its worst outcome.

## How a record is judged

As DuckDB's own runner judges it (`test/sqlite/result_helper.cpp` at the tag): values are
written as DuckDB's `CAST(v AS VARCHAR)` (NULL as `NULL`, an empty string as `(empty)`, a
boolean as `1`/`0`), `rowsort` and `valuesort` sort that text, a result written as `N values
hashing to H` is compared by MD5, and a value whose text differs is equal only in a numeric
column, where the expected text cast to the column's type must equal the answer: integers and
decimals exactly, floats within 1% of the answer plus 1e-8 (DuckDB's `ApproxEqual`). The
column count must match the type letters, and an expected row splits on tabs as DuckDB splits
it (empty pieces dropped). `statement error` passes on an error containing the expected
message. The harness is stricter than DuckDB's runner in two places: a result compared by
label or past the hash threshold is also compared value by value when the file lists the
values; and a `nosort` answer of several distinct rows is wrong if Burrmill's plan leaves
their order unfixed (a union or a merge of partitions with no sort above it) or a rerun
answers in another order, even when this run's order matched, since DuckDB's file fixes it.

Burrmill answers queries only, so the harness keeps the tables the files build: `CREATE
TABLE`, `INSERT`, `UPDATE`, `DELETE`, `DROP`, `CREATE VIEW` and transactions are mapped onto
`Engine::register_batch`, `register_view` and `drop_relation`, with every value computed by
Burrmill (the column types are its `CAST(NULL AS type)`, the rows its answer to the `VALUES`
or `SELECT` cast to the column types, an update its `CASE WHEN` over the table). NOT NULL,
PRIMARY KEY and UNIQUE are checked by the harness; a record the harness decides alone (a
`DROP`, a constraint violation) is skipped, not passed, and so is a write DuckDB refuses that
the mapping accepts (a default, a clause or a constraint it does not check). Settings that
change no answer (`threads`, `memory_limit`, profiling, verification, compression) are
skipped, and after a resource limit (`memory_limit`, `max_temp_directory_size`, ...) an error
DuckDB raises under it is skipped too, as the harness does not impose it. Any other setting,
`ATTACH`, `COPY`, `ALTER`, `CREATE MACRO` and the like skip the rest of the file, and so does a
failed setup write, a write the engine is handed inside a query (`INSERT ... RETURNING`, a DML
CTE), `EXPLAIN ANALYZE`, and a write on a named connection, so no answer is compared against
state DuckDB never had.
Each file runs in its own process on one thread, each statement under a 30-second deadline.
